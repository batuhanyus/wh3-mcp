# WH3 MCP file transport protocol v2

Protocol v2 is the file-level contract between the Node MCP server and the Lua mod. It replaces the uncorrelated v1 `{command, params}` / `{status, ...}` exchange. Protocol v2 is deliberately small: there is still at most one published command filename and one published result filename, but every message has durable identity and publication is atomic.

## Request envelope

```json
{
  "protocol": 2,
  "session_id": "server-1730000000000-8d07...",
  "request_id": 42,
  "command": "get_status",
  "params": {}
}
```

Fields:

- `protocol`: integer, exactly `2`.
- `session_id`: non-empty opaque string generated by the Node server at process start. A server restart creates a new session ID.
- `request_id`: positive integer, monotonically increasing within one Node session. A request ID MUST NOT be reused for a different request in the same session.
- `command`: non-empty string.
- `params`: JSON object. Use `{}` when a command has no parameters.

## Reply envelope

Success:

```json
{
  "protocol": 2,
  "session_id": "server-1730000000000-8d07...",
  "request_id": 42,
  "status": "ok",
  "result": { "turn": 8 }
}
```

Failure:

```json
{
  "protocol": 2,
  "session_id": "server-1730000000000-8d07...",
  "request_id": 42,
  "status": "error",
  "error": {
    "code": "COMMAND_FAILED",
    "message": "get_status failed",
    "details": { "context": "frontend" }
  }
}
```

Fields common to every reply are `protocol`, `session_id`, `request_id`, and `status`. `status` is exactly `ok` or `error`. An `ok` reply may contain `result` and MUST NOT contain `error`. An `error` reply MUST contain an error object with a known `code` and non-empty `message`; it MUST NOT contain `result`.

## Error categories

Protocol v2 reserves these error codes:

- `GAME_NOT_RUNNING`: the server cannot find a live WH3 process.
- `NOT_READY`: the Lua context exists but has not completed the v2 bootstrap handshake.
- `IO_FAILURE`: command/result publication, rename, read, or cleanup failed.
- `INVALID_REQUEST`: malformed JSON or invalid request fields.
- `INVALID_RESPONSE`: malformed JSON or invalid reply fields.
- `PROTOCOL_MISMATCH`: the peer supplied a protocol version other than 2.
- `STALE_RESPONSE`: a response/request belongs to an inactive session or an obsolete request identity.
- `COMMAND_TIMEOUT`: queue acquisition or game execution exceeded its deadline.
- `CONTEXT_CHANGED`: Lua context reloaded while a request outcome could no longer be replayed safely.
- `GAME_EXITED`: WH3 exited while the request was in flight.
- `COMMAND_FAILED`: the command was accepted but command-specific execution failed.
- `UNSUPPORTED_CAPABILITY`: the active WH3 context does not expose a required engine capability.

Additional codes require a protocol documentation change and validator update.

## Bootstrap and readiness

The deterministic bootstrap command is `__handshake`.

1. On server startup, Node creates a fresh `session_id`, quarantines protocol-file leftovers, and publishes a v2 `__handshake` request.
2. Lua validates the envelope before dispatch. The handshake params include `server_started_at_ms`; Lua rejects a handshake demonstrably older than the currently adopted server session. A valid newer handshake adopts the server session, resets the in-memory reply cache, preserves the monotonic acceptance ledger for that session when appropriate, and replies with `result.ready=true`, its `instance` token, and current `context`.
3. Node becomes ready only after a valid, identity-matching handshake reply. It never infers readiness from the existence or disappearance of a file.
4. A fresh Lua context starts `ready=false`. A non-handshake request received before bootstrap returns `NOT_READY` without dispatching the command. Node may then handshake and submit the user command as a new request ID.
5. A protocol version mismatch fails visibly. There is no v1 fallback.

Example bootstrap:

```text
Node -> {protocol:2, session_id:"S1", request_id:1, command:"__handshake", params:{}}
Lua  -> {protocol:2, session_id:"S1", request_id:1, status:"ok",
         result:{ready:true, instance:"lua-...", context:"frontend"}}
```

## Exactly-once acceptance, dedupe, and replay

Within one server session, Lua MUST NOT dispatch the same accepted `request_id` twice.

Lua maintains two bounded pieces of state:

1. a monotonic acceptance ledger (`last_request_id`) persisted to a small sidecar file so a main-menu/campaign/battle Lua-context reload cannot cause an already accepted request to execute again; and
2. an in-context bounded reply cache for recent request IDs.

Behaviour:

- duplicate ID still in the reply cache: replay the cached reply, do not dispatch;
- ID at or below `last_request_id` but reply no longer cached (including after Lua context reload): return `CONTEXT_CHANGED`/`STALE_RESPONSE` with outcome described as unknown, do not dispatch;
- request ID greater than `last_request_id`: validate readiness, record acceptance before dispatch, then execute once;
- handshake for a genuinely new `session_id`: adopts the new session and starts a new request sequence for that server process. Requests from an older session are rejected once the new session is active.

This is exactly-once **acceptance**, not a transactional guarantee over the game engine. If WH3 crashes after a side effect but before the reply is durably published, the server MUST report the outcome as unknown. It MUST NOT promise exactly-once game-side effects across process crash/relaunch.

The reply cache is bounded; eviction never makes an old request executable again because the acceptance ledger remains authoritative.


## Correlated context transitions

Context-changing commands carry the mandatory `session_id` and `request_id` and may additionally carry `transition_id`; protocol-managed transitions also carry `transition_destination`. Lua echoes `transition_id` in the reply. A successful transition completion includes `result.transition` with the same transition identity, the expected destination, the observed context and an outcome. Node validates those fields before accepting the completion. Deferred context-transition markers persist the same identity plus the expected destination. A marker may complete a request only when its session/request/transition identity still matches the persisted accepted request; stale, duplicated or otherwise uncorrelated markers are quarantined. The persisted session ledger remembers the last completed transition identity so a copied deferred marker cannot resurrect completed work after another Lua reload.

The Node transport exposes lifecycle states `READY`, `TRANSITIONING`, `RECONNECTING`, `FAILED` and `GAME_EXITED`. After a successful context reload, Node marks the old Lua instance unready and performs a fresh handshake before an ordinary command is issued. A timed-out or otherwise ambiguous state-changing operation is not automatically replayed. If reconnect lands in a context inconsistent with the expected destination, the next attempted operation receives `CONTEXT_CHANGED` and the ambiguous mutation remains unreplayed.

## Atomic publication and ownership

Established filenames remain:

- `wh3_mcp_command.json`: Node-owned publication, Lua-owned consumption.
- `wh3_mcp_result.json`: Lua-owned publication, Node-owned consumption.

Writers MUST publish atomically on the same filesystem:

1. write complete JSON to a unique temporary file;
2. flush and close it;
3. rename it to the established filename;
4. on Windows, if the target unexpectedly exists, move the old target to quarantine first rather than relying on POSIX overwrite semantics.

Readers never treat a temporary file as a message. A JSON parse failure is an error, not evidence that a partial write should be executed.

Node owns removal/quarantine of result files after reading and validating them. Lua owns removal of a consumed command file. Neither side blindly deletes the peer's only valid response before it has been read and identity-checked.

Prior-run leftovers, malformed files, mismatched protocol/session/request IDs, and late post-timeout replies are moved to a quarantine area when possible. They are diagnostic evidence, never a successful reply to a different request.

## Timeouts and queueing

Node serialises every game command through one exclusive command transport. A call has two explicit deadlines:

- queue deadline: maximum wait to acquire the one in-flight slot;
- execution deadline: maximum wait, after publication, for an identity-matching reply.

A call whose queue deadline expires is removed from the queue and MUST NOT execute later. An execution timeout includes `session_id` and `request_id`. A late result is quarantined on the next transport observation and cannot satisfy a newer request.

Long-running MCP tools that repeatedly poll the game use the same transport for every command; no direct protocol-file path is permitted beside the transport.

## Session and context reset examples

Lua context reload while the Node server remains alive:

```text
Node -> S1 / 55 / get_situation
Lua  -> NOT_READY (fresh Lua context, command not dispatched)
Node -> S1 / 56 / __handshake
Lua  -> S1 / 56 / ok {ready:true, instance:"lua-new", context:"campaign"}
Node -> S1 / 57 / get_situation
Lua  -> S1 / 57 / ok {...}
```

Server restart while the game remains alive:

```text
old Node session: S1
new Node -> S2 / 1 / __handshake
Lua      -> S2 / 1 / ok {ready:true,...}
late S1 result -> quarantined/rejected; it can never satisfy S2
```

Crash ambiguity:

```text
Node -> S2 / 9 / mutate_game_state
WH3 accepts and performs the mutation, then exits before publishing a reply
Node -> error GAME_EXITED or COMMAND_TIMEOUT, outcome:"unknown"
```

## A01 hand-off call sites

A01 defines the contract and validators only. The transport migration in A02 must replace the v1 assumptions at:

- `server/index.js`: `sendCommand()`, `clearFiles()`, and every MCP handler that directly calls either;
- `pack/script/_lib/mod/wh3_mcp.lua`: command-file parse/dispatch in `poll_body()`, every `RESULT_FILE` publication path, context-transition marker handling, and polling bootstrap readiness.

A03 additionally owns the timer capability checks and singleton lifecycle in the Lua initialisation block.
